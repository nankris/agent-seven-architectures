# The same AI agent in seven architectures, under failure

**Question.** When a tool call times out or the process dies mid-run, which agent architecture keeps doing the job right, and which one sends the refund twice? We build one task-doing agent in LangGraph seven ways and break every version at the same fixed points.

**Builds on.** Brahim Guaali, *I rebuilt one AI agent seven times to understand graph engineering* ([Medium](https://medium.com/@brahimg/i-rebuilt-one-ai-agent-seven-times-to-understand-graph-engineering-80b9983cd921)), code [brahim-guaali/graph-engineering-from-first-principles](https://github.com/brahim-guaali/graph-engineering-from-first-principles) (MIT). We reuse its job (food-delivery refunds), its policy clauses, its two narrow model judgments (`classify`, `decide`) and its stage order, and adapt it to an open model and a fault-injection harness.

## Setup

- **Agent job.** A customer message comes in. The agent must look up the order, the policy and the fraud score, then do exactly the right side effects: `issue_refund` (correct amount), `issue_credit` ($5), `create_ticket` (queue `risk` for fraud, `support` for non-refund complaints), and `notify_customer` (email). Refunds over $500 need manager approval first. Side-effecting tools are mocks that write to a ledger, so every committed effect is counted.
- **Tasks.** 72 tasks generated by `scripts/tasks.py` (fixed seed 133) from the source's nine case types: late >45 min, late big order (>$500, needs approval), missing item, spoiled item, slightly late, cancelled after cooking, fraud, rider/app complaint, prompt injection. Ground truth computed by code from order facts. **Pilot: P01-P12 (12 tasks). Confirmatory: T01-T60 (60 fresh tasks never used in the pilot).**
- **Model.** Qwen3-8B (FP8 weights, `Qwen/Qwen3-8B-FP8`), served by vLLM on a Colab L4 with Hermes tool calling and JSON-schema structured output; thinking disabled; temperature 0.7, top-p 0.8, top-k 20; per-request seed derived from the run seed. Token counts come from the server's `usage` field.
- **Seven architectures** (all LangGraph 1.1, `scripts/agents.py`):

| ID | Architecture | What it adds |
|---|---|---|
| V1 | ReAct loop | One model node + tool node; transcript is the state. Tool errors are returned to the model (it decides whether to retry: naive retry). Crash: restart from scratch. |
| V2 | + structured state | Typed state, two narrow model calls (`classify`, `decide`), code routes, sequential lookups. Any failure: runner restarts the run from scratch. |
| V3 | + parallel nodes | V2 with the three lookups fanned out in one superstep. |
| V4 | + checkpointing | V3 + `SqliteSaver`; after a failure/crash the runner resumes the thread (only unfinished nodes re-run). No idempotency keys (source stage 4). |
| V5 | + human approval | V3 + `interrupt()` before refunds > $500, simulated approver, `Command(resume=...)`. In-memory checkpointer, so a crash still loses the run. |
| V6 | + retries | V3 + `RetryPolicy` (3 attempts) on every node + idempotency key (`run:node`) on every side effect (source stages 5-6). |
| V7 | full combination | V3 + SqliteSaver + interrupt approval + RetryPolicy + idempotency keys. |

  In V1-V4 and V6 the approval is a synchronous call to the same simulated approver (V1 via a `request_manager_approval` tool the model must choose to call; V2-V4, V6 via a code-routed node). The simulated approver approves iff amount <= order total and fraud score <= 0.7.
- **Faults (fixed points, identical across architectures, each fires at most once per run):**
  - `clean`: none.
  - `timeout`: the first `get_fraud_signals` call hangs 2 s then raises a timeout (no side effect); the first money-type side effect (refund/credit/ticket) **commits and then** times out (lost acknowledgement).
  - `crash`: the first money-type side effect commits, then the process dies (`ProcessCrash`, a BaseException nothing in-process catches). The runner starts a "new process" (fresh graph object, same thread id).
  - Outer runner: at most 3 process starts per run. ReAct gets at most 14 model calls per start.
- **Design.** 7 architectures x 3 conditions x tasks x seeds, every task run under every cell (fully paired). Pilot: 12 tasks x 1 seed (252 runs). Confirmatory: 60 tasks x 3 seeds (0, 1, 2) = 3,780 runs.

## Metrics (per run)

- **Task success**: the final ledger is exactly right (refund total equals the expected amount with exactly one refund if one is due, exactly one $5 credit iff due, exactly one ticket in the right queue iff due, at least one customer notification, no refund > $500 without prior approval).
- **Duplicate side effects** (`any_dup_money`): the run committed the same money-type effect (refund, credit, ticket) more than once. Duplicate notifications are reported separately.
- **Model calls**, **prompt and completion tokens** (from vLLM), **latency** (wall clock, includes 0.25 s mock latency per tool call and 2 s per timeout).
- **Recovery after the timeout**: success rate in the `timeout` condition; also restarts and extra model calls relative to the same task's clean run.

## Pre-registered hypotheses (from the source article, before any pilot)

The source's evidence: on 12 cases with Gemini, the loop used 39 model calls vs 23 for the graph (-41%) and 32,892 vs 7,082 input tokens (-78%); accuracy was a tie (12/12 each). Its failure demos: a timeout loses the loop's run; checkpointing alone re-pays after a crash ("without a key: paid twice"); run+node idempotency keys pay once; checkpoints resume from the last round.

Statistics: unit of analysis = task (each task's value is averaged over seeds; paired across architectures). 95% percentile bootstrap CI over tasks, 10,000 resamples, seed 0. Decision rule for every hypothesis: **PROVEN** if the whole 95% CI is beyond the margin in the predicted direction; **DISPROVEN** if the whole CI is on the other side of the margin (the effect is smaller than the margin or reversed); **INCONCLUSIVE** otherwise.

| # | Hypothesis | Metric, cells | Prediction (source) | Margin and why |
|---|---|---|---|---|
| H1 (primary) | Checkpointing + idempotent retries cut duplicate side effects vs plain ReAct with naive retry | `any_dup_money` rate, V1 minus V7, faulted runs (timeout + crash pooled) | V7 ~0%, V1 well above 0 (source: unkeyed replay pays twice) | 5 pp: one duplicate refund per 20 failures is already an unacceptable money leak |
| H2 (primary) | Structured state reduces model calls | relative reduction in model calls per task, V1 vs V2, clean | -41% (source: 39 to 23) | 25%: below this the extra engineering is hard to justify on cost alone |
| H3 | Structured state reduces prompt tokens | relative reduction in prompt tokens, V1 vs V2, clean | -78% | 50% |
| H4 | Checkpointing avoids re-doing model work after a crash | extra model calls (crash minus clean, same task), V3 minus V4 | V3 redoes ~2 calls, V4 ~0 | 1 model call per crashed run |
| H5 | Checkpointing alone does not prevent duplicates after a crash | `any_dup_money` rate, V4, crash | high (source: "paid twice") | V4 crash duplicate rate CI lower bound > 50% = PROVEN |
| H6 | Accuracy is a tie when nothing fails | success rate, V7 minus V1, clean | 0 (source: 12/12 vs 12/12) | equivalence +-10 pp: PROVEN if the whole CI is inside (-10, +10) pp; DISPROVEN if wholly outside |
| H7 | Parallel lookups cut latency | latency per run, V2 minus V3, clean | ~0.5 s (two 0.25 s mock tool calls overlap) | 0.25 s |
| H8 | Full graph recovers from the timeout | success rate, V7 minus V1, timeout | positive | 10 pp |

The pilot (P01-P12, 1 seed) is used only to check that faults fire, that all architectures run, and to read off the size of the V1 duplicate rate. Any change to predictions or margins after the pilot will be written in a dated "Pilot amendment" section below and committed **before** the confirmatory run; hypotheses themselves are not reworded.

## Pilot amendment (18 Oct 2026, written before the confirmatory run)

- **First pilot attempt discarded as a plumbing failure** (`results/runs_pilot_discarded.jsonl`, kept for transparency): with vLLM's default JSON-schema decoding, Qwen3-8B sometimes emitted runaway whitespace (structured outputs >20,000 lines) until max_tokens, so `classify`/`decide` failed to parse in a large share of V2-V7 runs. Fix: vLLM restarted with `--structured-outputs-config '{"disable_any_whitespace": true}'` (and `--max-num-seqs 48`). No agent, task, fault or scoring code changed. The pilot was rerun on the same 12 pilot tasks (`results/runs_pilot.jsonl`, 252 runs, 138 s, 0 parse failures, every fault fired in 12/12 faulted runs per cell).
- **Pilot readings** (12 tasks, 1 seed; `results/summary_pilot.json`): V1 faulted duplicate rate 71% vs V7 0%; model calls V1 6.0 vs V2 1.9 per clean run; prompt tokens 7,550 vs 643; V3 re-does ~1.9 model calls after a crash, V4 0; V4 crash duplicates 100%; clean success V1 67% vs V7 92%; V7 timeout success 92% vs V1 0%.
- **Latency caveat found in the pilot**: runs execute 24 at a time against one vLLM server, so per-run latency includes GPU queueing (clean V2 vs V3 differed by 0.5 s with a CI of about +-12 s). H7 is therefore likely underpowered at 60 tasks. Predictions, margins and the H7 metric are **unchanged**; this is noted so an INCONCLUSIVE H7 is not a surprise.
- Nothing else changes. Confirmatory run: T01-T60 (fresh), seeds 0, 1, 2, same server flags. (Executed with 32 concurrent workers, not 24; see results/incident_double_driver.md for an aborted first attempt.)
